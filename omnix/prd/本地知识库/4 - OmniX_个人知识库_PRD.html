一、概述

1.1 背景与问题

知识工作者（研究者、写作者、开发者、法务/咨询等）的知识资产大量沉淀在本地文件系统中：Markdown 笔记、PDF 论文/合同、Word 文档、Excel 表格、代码仓库、PPT 材料等。当前这些资料存在三大痛点：

  • 散而难查：资料分散在多个目录，靠记忆和文件名检索，跨文件、跨语义的"第二跳"问题几乎无法回答。
  • 不可问答：用户想要的是"基于我自己的资料回答我"，而不是再去搜索一遍；但通用大模型没有这些私有资料，且极易编造。
  • 不愿上云：资料往往含敏感/私有内容，用户不希望被强制上传到第三方云端，要求数据留在本地、可追溯源头。

1.2 产品目标

OmniX 个人知识库的目标是：把用户本地的任意文件夹登记为一个可管理的知识库实例，将其中的文件自动转化为"可搜索、可提问、可追溯"的页面体系，并以混合检索 + 引用回答的方式让用户用自然语言提问，回答始终带来源定位、不编造。

1.3 三条产品原则 ★核心

本地优先（Local First）：默认数据落在用户机器或受控数据库，非强依赖云托管；原文件始终留在绑定目录，不移动、不改写、不生成解析副本。
可追溯（Traceable）：每一段回答、每一条检索命中都能回原文核验；页面、搜索结果、答案均提供回到原文件的入口；状态机强制暴露真实进度。
不编造（No Hallucination）：检索与回答严格基于证据；证据不足时返回"无法确认"而非硬编；无回溯证据不得写入 Compiled Truth。

1.4 核心闭环

个人知识库以一条端到端闭环组织能力，而非零散功能堆叠：

① 本地目录

用户绑定一个本地文件夹，作为知识库的资料源根目录。

② 写入链

页面 + 片段 + 图谱 + 时间线，把原文件转化为可检索的知识。

③ 搜索链

混合检索（关键词+语义+图谱+时间）+ 引用回答，回答带来源。

④ 持续维护

增量同步、健康暴露、向量回填，知识库随时间累积而非重复构建。

1.5 用户画像

角色典型场景对产品的核心诉求
研究者 / 写作者管理大量 PDF / Markdown 文献，常需跨文档对比观点问答带引用、可追溯原文页码、不被编造
开发者把代码仓库、设计文档、Wiki 纳入知识库代码按同步策略解析、本地优先、不污染原仓库
法务 / 咨询 / 普通用户合同、案例、资料混杂，只想"问一句就拿答案"不需懂向量/RRF/资料源即可上手，失败原因可见

1.6 非目标（Non-goals）★范围控制

  • 不做逐文件上传 / 手工粘贴导入：V1 仅支持"选文件夹绑定"入口，保持资料源边界清晰、可监听。
  • 不做多用户团队共享（V1）：V1 为单用户本地优先；多用户、共享、外部智能体接入作为后续扩展，但权限隔离框架需在 V1 预留。
  • 不做自动内容生成 / 写作：知识库只"组织与回答"用户已有资料，不替用户创作新内容（回答层可基于资料生成结论，但须引用，不编造）。
  • 不做强依赖云托管：嵌入/重排等可选能力可本地或受控部署，但不得因云端不可用而阻断关键词检索这一基础能力。

1.7 用户故事

作为 知识工作者，我希望 把一个本地资料文件夹绑定为知识库并等待自动同步，以便 之后能用自然语言提问并获得带来源引用的回答，而不必手动翻找文件。
作为 普通用户，我希望 清楚看到每个文件当前处理到哪一步、为什么失败，以便 在不理解底层技术概念的情况下也能安心使用与排查。
作为 注重隐私的用户，我希望 原文件始终留在我的机器上且不被改动，以便 确信我的私有资料没有被上传或破坏。

三、详细设计

🔹 3.1 知识库与资料源管理

功能描述

把"用户本地目录"登记为可管理的知识库实例，并约定资料源边界。系统以"知识库实例 + 资料源"两层轴组织数据；绑定目录后自动登记为默认资料源根目录，界面只展示这一条绑定关系，不可修改。

字段设计（知识库实例 KB_Instance）

字段类型必填说明
知识库ID (kb_id)UUID✅系统生成，全局唯一，作为所有页面/片段/索引的外键
名称 (name)文本✅用户自定义，最大 50 字符；支持中英文、数字、下划线；同用户下唯一
图标img✅知识库的视觉标识，支持上传图标，未上传时显示默认图标（标题首字+随机色生成的图标，保存），支持 JPG、PNG、GIF 格式，图片大小不超过 1MB，建议尺寸 128×128px（限制500x500px以内）
绑定目录绝对路径 (bound_path)文本(绝对路径)✅用户选择的本地文件夹绝对路径，规范化（去 trailing slash、解析符号链接）后存储
资料源类型 (source_type)枚举✅本地文件夹
同步策略 (sync_strategy)系统固定系统系统统一同步机制：①首次绑定触发全量扫描；②绑定后持续监听目录变更；③每 1 分钟自动执行增量更新；④全程支持手动"立即同步"。以上四项共同构成知识库的完整同步策略。
知识库状态 (kb_status)枚举✅知识库整体处理状态（聚合推导），三态：待处理 / 处理中 / 已完成（详见 3.3 知识库状态定义）
文件状态 (file_status)枚举✅知识库内每个文件的独立处理状态：待解析 / 解析中 / 已完成 / 暂不支持 / 解析失败（详见 3.3 文件状态定义）
创建人系统记录自动记录词条创建者的用户名，新增时自动填充，不可编辑
创建时间系统记录自动记录词条创建时间（精确到秒），新增时自动填充，不可编辑
更新人系统记录自动记录最后一次编辑者的用户名，编辑时自动更新，不可手动修改
更新时间系统记录自动记录最后一次编辑时间（精确到秒），编辑时自动更新，不可手动修改

交互细节

  • 新建入口：知识库列表页右上角"新建知识库"按钮 → 弹出表单（名称输入 + 文件夹选择器）。
  • 文件夹选择：调用系统原生文件夹选择器，仅返回绝对路径；禁止手动粘贴相对路径或网络盘挂载以外的非法路径。
  • 实时校验：名称输入框失焦时实时校验同用户唯一性；路径选择后即时做存在性/可读性预检，预检失败按钮置灰。
  • 提交反馈：提交成功后跳转到知识库详情，顶部显示"正在首次扫描…"状态条，可后台运行。

序号规则说明

🔹 3.2 写入链（资料导入与知识化）

功能描述

把本地文件从"原文件"转为"可搜索、可提问、可追溯"的页面体系，分八节点推进：扫描 → 变更识别 → 文件路由 → 解析 → 标准化 → 切分索引 → 向量化（可选）→ 图谱补建。原文件始终零改动，无解析器的文件标记"暂不支持/等待解析"而非伪装为已知识化。

交互细节

  • 进度可见：导入过程展示"已扫描 N / 已解析 M / 暂不支持 K / 失败 J"的实时计数，而非单一"处理中"。

  • 回填入口：资料源健康面板提供"重试失败项""仅回填向量"按钮，定向执行不必全量重扫。

🔹 3.3 状态机（知识库+文件）

功能描述

状态机分为两个层级：知识库状态（kb_status，宏观聚合）反映知识库整体处理进度，由其内所有文件状态聚合推导；文件状态（file_status，微观推进）反映知识库内每个文件在写入链各节点的独立处理进度。两级状态都用可解释的状态替代模糊的"导入成功"，让进度真实可见、不可夸大。

知识库状态定义（字段：kb_status）

知识库状态为聚合推导状态，不独立写入——由其内所有文件的 file_status 实时聚合计算。共三种状态：

状态含义用户可做什么
待处理知识库已创建并绑定目录，但尚未开始扫描与解析，知识库内无任何文件进入处理流程（文件清单为空或全部未扫描）查看知识库配置，等待自动扫描或手动触发同步
处理中知识库正在扫描/解析/向量化，存在尚未到达终态的文件（ 待解析 / 解析中）查看实时进度，对已就绪（已完成）的文件进行检索问答
已完成知识库内所有文件均已到达终态（已完成 / 暂不支持 / 解析失败），无任何待处理文件自然语言搜索、问答、追溯；查看健康报告处理失败项
💡 聚合规则：当存在"待解析/解析中"的文件时 → 处理中；全部到达终态（已完成/暂不支持/解析失败）后 → 已完成；知识库未开始扫描时 → 待处理。新增文件（增量同步）会使"已完成"回流为"处理中"。

文件状态定义（字段：file_status / page_status）

文件状态针对知识库内每个独立文件，反映其在写入链各节点的处理进度。共六个状态：

状态含义用户可做什么
暂不支持无对应解析器，等待能力接入查看文件类型和原因，忽略
解析中页面已经开始解析并处理，包括文件解析，向量化处理等查看来源定位，编辑原文件
已完成页面/关键词/向量就绪，可问答追溯自然语言搜索、问答、追溯
解析失败解析或处理过程报错查看原因、重试或忽略

功能清单

序号功能名称优先级功能描述
1文件状态写入与持久化P0每个文件/页面在写入链各节点刷新 file_status，持久化并记录变更时间
2知识库状态聚合推导P0kb_status 由知识库内所有 file_status 实时聚合推导，无需独立写入；文件状态变更时自动重算
3两级状态展示P0知识库列表展示 kb_status 徽标（待处理/处理中/已完成），详情页内同时展示文件级 file_status；禁止用"成功"掩盖"待完成"
4知识库状态回流P0增量同步新增文件时，kb_status 从"已完成"自动回流为"处理中"；全部到达终态后恢复"已完成"
5降级态提示P1向量不可用时显式标注"向量待完成"，搜索结果注明"当前仅关键词+图谱"

交互细节

  • 知识库级徽标：知识库列表/卡片展示 kb_status 徽标——灰=待处理，蓝=处理中，绿=已完成；颜色与文案一致，避免歧义。
  • 文件级徽标：知识库详情内文件列表展示 file_status 徽标——灰=待解析，黄=解析中/暂不支持，绿=已完成，红=解析失败；悬停弹出"当前含义 + 你还能做什么 + 现在还不能做什么"三行说明。
  • 健康汇总：知识库详情页顶部健康条按文件状态聚合计数（如 12 已完成 / 3 解析中 / 1 暂不支持 / 1 解析失败），同时展示知识库整体状态。
  • 检索可用性提示：当用户对"关键词可检索但未向量化"的资料提问语义问题时，提示"该资料暂仅支持关键词检索，语义匹配可能不全"。

特殊说明

序号规则说明
1回流而非删除"已隔离/待修复"经修复后回流到"待解析/页面已写入"，不删除底层记录，保证可追溯
2知识库状态不可手动设置kb_status 为聚合推导状态，仅由文件状态实时计算，禁止任何接口或界面手动覆写；增量同步新增文件时自动从"已完成"回流为"处理中"
3已完成≠全部成功kb_status 为"已完成"仅表示所有文件到达终态（含暂不支持/解析失败），不代表零失败；健康面板仍须暴露失败项数量

🔹 3.4 搜索链（检索与回答）

功能描述

以"关键词 + 语义 + 知识图谱 + 时间证据"为混合检索基础，拆分为检索层与回答层。检索层做意图识别、多路召回、RRF 融合、多层去重与重排；回答层读完整页面生成结论、引用、冲突与信息缺口，严格不编造，并内置降级与三类空结果区分。

  • 回答视图：结论在上，引用卡片在下（含来源文件、页码/位置、"查看原文"按钮）；冲突与缺口以独立区块呈现。
  • 降级提示：处于降级时，回答区顶部黄条提示"当前仅关键词+图谱检索，语义匹配可能不全"。
  • 三类空结果文案：无权限→"你没有访问该知识库/资料的权限"；无命中→"没有找到相关内容"；证据不足→"找到相关资料，但不足以确认该问题，以下为相关信息"。

4重名知识库名称失焦实时校验，提示"知识库名称已存在"；后端兜底拦截同用户唯一
5文件无对应解析器标记"暂不支持/等待解析"，不进入可检索集合，清单红色展示并说明文件类型禁止伪装知识化
6解析失败（格式损坏）ParseRecord 标记失败并保留待修复记录；健康面板计入待修复；可重试不静默丢弃
7高噪声内容隔离并排除检索，状态置"已隔离/待修复"；保留底层记录可恢复可回退
8向量化服务不可用页面状态标"向量待完成"，搜索降级为仅关键词+图谱，结果声明降级不报完全可用
9嵌入模型/维度更换旧向量标失效，触发定向回填；回填完成前不混用向量空间空间隔离
10检索无权限（外部调用方）返回"拒绝"语义，不返回"未找到"，避免泄露资源存在性拒绝≠未找到
11检索无命中返回"未找到相关内容"，明确告知而非空泛报错三类空结果之一
12检索证据不足返回"无法确认"并附已有相关信息与缺口，绝不编造结论不编造
13多库查询串库强制 scope(kb_id+source_root) 校验，越权请求返回拒绝两层约束
14智能体越权访问校验 Grant 授权范围，超出则返回拒绝且不暴露被拒资源授权前置
15原文件被外部删除增量扫描识别"已删除"，页面软删除并保留来源凭据；检索不再召回该页可追溯
16原文件被外部移动/重命名据 content_hash 识别为"重命名"，更新路径并保持页面标识，不重建幂等
17原文件被外部修改哈希变更识别"已修改"，重新解析并更新页面与时间线增量更新
18绑定目录整体不可达（盘卸载）知识库健康标记"资料源不可访问"，提示用户；kb_status 保持当前值（不新增异常态），文件状态不变，增量扫描暂停；不自动改扫其他目录不静默改扫
19超大目录性能首次扫描分批进行，实时上报进度；超限文件单独标记，不阻塞整体异步+批处理
20语义缓存故障缓存读取失败直接回退实时检索，不阻断回答故障不阻断
21缓存跨源复用风险缓存键含 scope+嵌入空间+检索配置，跨源/跨空间不命中防串库
22并发回填冲突同一资料源回填按批次锁串行；失败项可单独重试，不必全量幂等
23夜间维护与用户操作冲突维护任务低优先级，遇用户主动操作让行；冲突整理基于追溯链可回滚V1.1
24解析器升级后行为变化据 parser_ver+哈希判定需重解析项，仅对变更项重建，不重做全目录版本重建
💡 以上 24 个边界场景覆盖了目录校验、解析失败、向量降级、串库越权、原文件外部变更、并发与缓存等核心风险点。其中 ★ 标记项（无权限拒绝、不编造、不静默改扫、禁止伪装知识化、本地优先兜底）是防幻觉与防数据事故的高压线，须写入验收用例。
